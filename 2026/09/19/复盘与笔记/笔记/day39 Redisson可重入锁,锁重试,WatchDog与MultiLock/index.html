day39 Redisson可重入锁、WatchDog与MultiLock

一、为什么使用 Redisson

上一阶段实现的 SimpleRedisLock 已经能借助线程标识和 Lua 脚本避免误删，但仍有四个不足：

问题 影响 Redisson 的对应能力
不可重入 同一线程再次获取同一把锁会失败，嵌套调用可能无法继续 使用 Hash 记录持有线程与重入次数
不可重试 获取失败后立即返回，无法在限定时间内等待 tryLock 支持等待并重试
固定超时释放 业务未执行完，锁可能先过期 WatchDog 自动续期
主从一致性 锁尚未同步时主节点故障，故障转移后可能丢锁 MultiLock 同时锁定多个独立节点

Redisson 是基于 Redis 的 Java 客户端，提供 RLock 等分布式对象。这里使用它的目的不是替换 Redis，而是复用其已经封装好的分布式锁语义与复杂并发处理。

三、可重入锁原理

3.1 Hash 存储结构

Redisson 的可重入锁使用 Redis Hash 保存锁状态：

  • Redis key 表示哪一把锁；
  • field 标识持有锁的客户端和线程；
  • value 是该线程的重入计数。

同一线程再次进入相同锁保护的代码时，不需要与自己竞争，只需增加计数。每次退出一层就减少计数，直到计数归零才真正删除锁。

3.2 获取锁流程

获取锁的判断与写入由 Lua 脚本原子执行：

  1. 锁 key 不存在：写入当前线程标识，计数设为 1，并设置过期时间，获取成功；
  2. 锁 key 已存在且包含当前线程标识：计数加 1，刷新过期时间，重入成功；
  3. 锁由其他线程持有：获取失败，返回锁的剩余存活时间。

返回 nil 表示首次获取或重入成功；返回剩余 TTL 表示锁正由其他线程持有。

3.3 释放锁流程

释放时同样需要用 Lua 保证“检查归属、修改计数、删除或续期”是一个原子操作：

  1. 判断锁是否存在以及是否属于当前线程；
  2. 不属于当前线程时不允许释放；
  3. 属于当前线程时将重入计数减 1；
  4. 计数仍大于 0，说明只退出了内层调用，刷新过期时间；
  5. 计数归零，才删除 Redis key，并通知等待该锁的线程。

因此，获取多少次就需要释放多少次。内层调用提前删除 key 会破坏外层业务的互斥性，重入计数正是为了避免这个问题。

四、锁重试与 WatchDog

4.1 有限等待与重试

带 waitTime 的 tryLock 并不是无休止地轮询 Redis，其主要流程是：

  1. 执行 Lua 脚本尝试获取锁；
  2. 返回 null 时获取成功；否则得到当前锁的剩余 TTL；
  3. 扣除本次操作耗时，若剩余等待时间小于等于 0，则返回失败；
  4. 订阅锁释放通知，并在剩余时间内等待；
  5. 收到通知或等待一段时间后再次尝试获取；
  6. 获取成功则返回，等待时间耗尽则失败。

这种“通知 + 再尝试”的方式减少了纯忙等造成的无效请求。tryLock() 无参调用则是立即尝试，不提供最大等待时间。

4.2 WatchDog 自动续期

固定过期时间无法预知业务究竟执行多久。租约太短会在业务结束前丢锁，租约太长又会使客户端故障后的锁长时间不释放。WatchDog 用自动续期协调这两个问题：

在本次学习对应的默认配置中，WatchDog 大约每 10 秒把锁续回 30 秒。续期仍会校验锁的线程标识，避免给别人的锁续期。

如果持锁客户端崩溃，续期任务也会停止，Redis 中的过期时间最终会清除锁，避免永久死锁。

注意：WatchDog 的“未设置过期时间”是指调用加锁方法时没有显式传入 leaseTime，不是 Redis key 没有 TTL。Redisson 仍会给锁设置内部租约并周期续期。

5.2 MultiLock 的组合方式

MultiLock 将多个独立 Redis 节点上的 RLock 组合为一把联锁。只有所有子锁都获取成功，整体才算成功；如果某个子锁获取失败或等待超时，需要释放本次已经获取的子锁。

5.3 代价与适用边界

MultiLock 通过“所有节点都成功”避免仅因单个节点丢失锁数据就重新取得完整锁，但可用性会降低：

  • 任一节点不可用，都可能导致整把锁获取失败；
  • 加锁与释放需要访问多个节点，网络和操作开销增加；
  • 它适合更重视锁安全、能够接受节点故障时暂时拒绝业务的场景。

因此它是在一致性与可用性之间做取舍，并不是无代价地解决所有分布式锁问题。

六、今日问题与注意事项

6.1 两个 RedissonClient 的注入歧义

  • 现象：RedissonConfig 同时声明 redissonClient1、redissonClient2，业务字段只写了 @Autowired private RedissonClient redissonClient;。
  • 原因：容器中有多个同类型 Bean，单纯按类型无法唯一确定注入目标。
  • 解决方向：单锁业务明确使用 @Qualifier("redissonClient1")，或者用 @Primary 指定默认客户端；MultiLock 业务则分别注入两个客户端并组合各自的 RLock。
  • 提醒：仅仅配置多个客户端并不会自动获得 MultiLock 语义。

6.2 显式租约与 WatchDog 不要混淆

  • tryLock(waitTime, leaseTime, unit)：按传入的固定 leaseTime 自动释放，通常不会为这次锁启用 WatchDog 自动续期；
  • 不显式传入 leaseTime：成功获取后由 WatchDog 按内部租约自动续期；
  • tryLock()：立即尝试获取，但成功后仍可使用 WatchDog；代码注释中的“默认时间 30 秒”不等同于 30 秒后无条件释放。

今日总结

模块 核心要点
Redisson 接入 通过 RedissonClient 获取 RLock，在 finally 中释放
可重入 Hash 的 field 标识线程，value 记录重入次数，计数归零才删除锁
原子性 获取、重入、释放等复合操作通过 Lua 脚本完成
锁重试 带等待时间的 tryLock 结合释放通知，在剩余时间内再次尝试
WatchDog 未显式指定固定租约时周期续期，释放或客户端失效后停止
MultiLock 所有独立节点都加锁成功才算成功，增强安全性但降低可用性
