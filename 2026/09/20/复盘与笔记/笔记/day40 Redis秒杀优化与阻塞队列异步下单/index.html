图中红色标记的”判断秒杀库存”和”校验一人一单”是判断逻辑，本身不产生订单数据，但每次都要查库，是主要耗时点。

二、优化整体思路

2.1 核心方案

将耗时短的判断逻辑前移到 Redis 中执行，判断通过后立即返回订单 id，实际下单操作异步执行：

  1. 新增秒杀券时，将库存缓存到 Redis，并用 Set 维护已下单用户
  2. 使用 Lua 脚本原子执行库存判断与一人一单检查
  3. 判断通过后，生成订单 id 并立即返回给用户
  4. 将订单信息放入阻塞队列
  5. 异步线程从队列取订单，完成数据库扣减库存和保存订单

图中左侧红色框为 Redis 预判断阶段，中间为阻塞队列，右侧为异步执行的数据库操作。用户请求只需完成左侧判断即可返回，不必等待右侧全部执行完毕。

2.2 优化前后对比

对比项 优化前 优化后

用途 数据结构 key 格式 value

已下单用户 Set seckill:order:{voucherId} 已下单的 userId 集合

库存使用 String 类型，通过 DECR 原子扣减；已下单用户使用 Set 类型，通过 SISMEMBER 判断是否重复下单、SADD 记录下单用户。

注意：当前方案将库存存为 String，未在 Redis 中保存秒杀时间信息，因此 Lua 脚本无法校验秒杀时间。

4.3 为什么后续不需要加锁

Lua 脚本在 Redis 中以原子方式执行”判断库存 → 判断一人一单 → 扣减库存 → 记录用户”这四步，中间不会被其他命令插入。加上 Redis 本身是单线程执行命令的，因此不存在并发安全问题。

这意味着后续异步线程执行数据库扣减库存和保存订单时，不需要再判断一人一单，也不需要加分布式锁。项目中的 createVoucherOrder 方法因此省略了旧版本中的 query().eq("user_id", userId).count() 查询。

5.1 阻塞队列

阻塞队列（BlockingQueue）是一种支持阻塞操作的队列：当队列为空时，take() 方法会阻塞等待，直到有元素入队才返回。项目使用 ArrayBlockingQueue：

容量设为 1024 * 1024（约 100 万），存储在 JVM 内存中。主线程将订单放入队列，异步线程从队列取出处理，实现生产者-消费者解耦。

六、今日问题与注意事项

6.1 ThreadLocal 在异步线程中失效

  • 现象：在异步线程（VoucherOrderHandler）中调用 UserHolder.getUser().getId() 抛出异常。
  • 原因：UserHolder 内部使用 ThreadLocal 存储用户信息，ThreadLocal 的数据只对当前线程可见。主线程（Tomcat 请求线程）存入的用户信息，异步线程无法读取。
  • 解决：在主线程中获取 userId 并存入 VoucherOrder 对象，异步线程通过 voucherOrder.getUserId() 读取，不再依赖 ThreadLocal。
  • 提醒：任何在拦截器中通过 ThreadLocal 设置的上下文信息（用户、请求头等），传递到异步线程时都需要显式传入对象，不能直接调用 ThreadLocal 的 getter。

6.2 阻塞队列方案的局限性

  • 内存限制：ArrayBlockingQueue 存储在 JVM 堆内存中，容量受限于内存大小。队列设置过大可能引发 OOM，过小则在高并发时可能拒绝入队。
  • 数据安全问题：服务突然宕机时，队列中尚未消费的订单会随内存丢失，用户已收到订单 id 但实际订单未落库。

这两个问题是阻塞队列作为消息队列的固有缺陷，后续可改用 Redis Stream 或专业消息队列（如 RabbitMQ、Kafka）解决，利用持久化和确认机制保证消息不丢失。

6.3 未校验秒杀时间

当前 Lua 脚本只判断库存和一人一单，没有校验秒杀时间。虽然前端会限制秒杀时间窗口，但后端缺少校验存在安全隐患。

改进思路：将 Redis 中库存的存储方式从 String 改为 Hash，同时存储库存、开始时间和结束时间，在 Lua 脚本中增加时间判断逻辑。
