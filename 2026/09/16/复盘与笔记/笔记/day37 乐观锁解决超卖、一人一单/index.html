day37 乐观锁解决超卖、一人一单与集群锁失效

一、乐观锁解决超卖问题

1.1 乐观锁思路

乐观锁：认为线程安全问题小概率发生，不添加锁，让线程并行执行，提高效率。在更新时判断数据是否与之前查询到的一致，一致则更新。

与悲观锁的对比：

维度 悲观锁 乐观锁
核心思想 认为冲突一定会发生，先加锁再操作 认为冲突概率低，不加锁，更新时判断
并发性 串行执行，吞吐量低 并行执行，吞吐量高
适用场景 写多读少，冲突概率高 读多写少，冲突概率低
本项目代表 synchronized + 编程式事务 .gt("stock", 0) 条件更新

1.4 .gt("stock", 0) 是乐观锁吗

这是随笔中的核心思考，结论如下：

写法 是否乐观锁 说明
.eq("stock", seckillVoucher.getStock()) 是 比较旧数据，一致才更新，符合乐观锁思想
.gt("stock", 0) 否（业务变体） 没有比较旧数据或版本号，只约束下限

注意：.gt("stock", 0) 不是经典乐观锁，也不是 MyBatis-Plus 的 @Version 版本号乐观锁。它是基于业务特点的数据库原子条件更新：利用 UPDATE 语句本身的原子性和 MySQL 行锁，在 WHERE 条件中约束 stock > 0，防止扣减到负数。

在悲观锁方案中，.gt("stock", 0) 的作用是兜底，防止锁失效后超卖。在乐观锁方案中，它作为主防超卖手段。两者的底层都依赖 MySQL 行锁机制。

二、一人一单

2.1 需求与问题

需求：同一个秒杀券，一个用户只能下一单。

并发问题：在”查询用户是否已下单 → 判断 → 写入订单”这个流程中，如果同一用户高并发访问，在订单未保存之前，多个线程都可以通过”未下单”的判断，导致一人多单。

2.2 锁粒度选择

加锁的目的是防止同一用户并发下单，因此锁粒度应该精确到用户级别。

锁对象 粒度 问题
VoucherOrderServiceImpl.class 类级别，所有请求串行 不同用户也串行，吞吐量极差
this 实例级别 同上，粒度太粗
userId.toString().intern() 用户级别 同一用户串行，不同用户并行，粒度精确

2.3 intern() 方法

userId 是 Long 类型，userId.toString() 每次调用会 new 一个新的 String 对象，不同线程拿到的是不同对象，无法互斥。必须使用 intern()：

  • 如果字符串常量池中已有该字符串，返回池中的引用
  • 如果没有，将当前字符串的引用放入池中，并返回

这样内容相同的字符串经过 intern() 后返回的是同一个引用，保证同一用户加的是同一把锁。

2.4 锁与事务的顺序

与 day36 的教训一致：锁的释放必须晚于事务提交。

如果锁在 createVoucherOrder 方法内部加（方法上有 @Transactional），则锁释放在方法内部，事务提交在方法返回后由代理完成，锁释放早于事务提交，其他线程在窗口期内能读到旧数据。

因此正确做法是将锁放在 seckillVoucher 方法中，包裹整个 createVoucherOrder 调用。

四、集群模式下 synchronized 锁失效

4.1 问题现象

经过测试，在集群模式（多实例部署）下，synchronized 锁会失效，仍会出现一人多单。

4.2 根本原因

synchronized 是 JVM 进程内锁。集群模式下每个服务器有独立的 JVM，字符串常量池也是各自的，锁对象互不感知，不同服务器的线程可以同时进入临界区。

4.3 解决方向

单机方案无法满足集群需求，需要跨进程的分布式锁，后续使用 Redis 分布式锁解决。

注意：当前基于 synchronized 的一人一单方案仅限单机单实例部署。生产环境的集群部署必须替换为 Redis 分布式锁。
