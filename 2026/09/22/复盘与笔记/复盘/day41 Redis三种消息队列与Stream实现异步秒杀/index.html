2. 核心知识点

消息队列基础

  • 消息队列（Message Queue）：存储和管理消息，也被称为消息代理
  • 为什么引入消息队列：
    • 异步响应，提高速度
    • 高峰时期大量请求先加入消息队列，后端按自己的处理能力匀速消耗
  • 消息队列的基本要求：
    1. JVM 以外，不受 JVM 内存限制
    2. 对数据进行持久化，保证数据安全
    3. 保证消息有序性
    4. 消费者需要对消息进行确认，确保消息至少被消费一次
  • 主流中间件有 RabbitMQ 等，这里使用 Redis 实现（3 种方式，了解即可）

方式一：基于 List 模拟

  • 利用 BLPOP、BRPOP 来取数据，才具有阻塞效果
  • 优点：基本满足前 3 条（存储在 Redis，可以持久化，list 是有序的）
  • 缺点：
    • 无法避免消息丢失，不满足第 4 条
    • 只支持单消费者

方式二：基于 PubSub（发布订阅）

  • Redis 发布订阅命令：
    1. PUBLISH channel message：将信息发送到指定的频道
    2. PSUBSCRIBE pattern [pattern ...]：订阅一个或多个符合给定模式的频道
    3. SUBSCRIBE channel [channel ...]：订阅给定的一个或多个频道的信息
  • 优点：采用发布订阅，支持多生产多消费者
  • 缺点：无法保证数据安全
    • 不支持持久化，无人订阅则丢失
    • 无法避免消息丢失
    • 消费者的消息堆积有上限，超出则丢失

消费者组解决了：

  1. 漏读问题，可以设置 “>” 从下一个未消费的消息开始
  2. 确认机制，未确认的消息保存在 pending-list，确保每个消息都被确认，防止消费者处理时异常导致消息丢失
  3. 一个消费者组中的消费者消费同一队列，可以提高效率
  4. 设置多个消费者组，可以实现多消费

实际选型建议

  1. 在实际开发中，list 与 PubSub 实现的消息队列缺点过多，不考虑
  2. 简单业务需求可以使用 Redis 的 Stream 消息队列
  3. 复杂场景，有复杂需求，还是要使用专业的中间件，如 RabbitMQ
